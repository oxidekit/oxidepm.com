Security and AI safety

OxidePM runs your services, so it matters who can tell it what to do. This page explains what an AI agent or an adapter is allowed to do, what gets recorded, and where the protections stop.

01

The connection decides who is asking

You talk to the daemon from your shell over daemon.sock. The daemon also binds agent.sock, and every connection on it counts as an AI agent, whatever it claims. The daemon decides from the connection a request arrived on, not from what the client says about itself, and a claim can only make a request stricter, never looser.

An agent that claims to be a person on agent.sock still gets agent limits. This binds an agent that goes through the agent socket or declares itself with OXIDEPM_ACTOR=ai:name. It does not stop a hostile process that runs as the same user and calls oxidepm without declaring anything: code that runs as you is you.

02

Permission tiers

Every request belongs to one of three tiers: safe, caution or dangerous. A person may make every request. An AI actor is held to the tier.

Tiers and what an AI actor may doA person: all tiers
Tier 1Safe
Requestsstatus, show, describe, logs, ping, hello
From an AI actorAllowed, on every app, protected ones too. Environment values and hook scripts stay hidden.
Tier 2Caution
Requestsstop, restart, reload
From an AI actorOnly on an app marked ai_control and not protected, and only when it names the apps (no all, no tags). Written to the audit log before it runs.
Tier 3Dangerous
Requestsstart (and a config file), delete, flush, kill, save, resurrect, show --reveal, describe --reveal
From an AI actorRefused. A person has to run these.

An AI actor also has its own rate limits: it can restart the same app once every 10 seconds and five times in ten minutes, so a looping agent can’t keep an app down.

03

Protected apps and dry runs

Mark an app protected and an AI actor can’t stop, restart or reload it, whatever ai_control says. It can still read status and logs. A person can still do everything. You change the markers of a running app with oxidepm policy set, without a restart.

Every command that changes something accepts --dry-run. The daemon runs the policy as for the real request and answers with a plan: the apps it would reach, in which order, and what it would refuse. It starts, stops and writes nothing.

04

Audit log

Everything an AI or an adapter asks for is recorded, and so is every caution or dangerous request by anyone. A request from an AI that changes something is written to disk before it runs, and refused if it cannot be.

The log is JSON lines in ~/.oxidepm/audit/. Environment values, hook scripts, the arguments themselves and log lines are never written. oxidepm audit reads it, even with the daemon down.

There is no tamper evidence beyond the file mode: a process with your rights can rewrite these files, as it can rewrite the database.

05

Adapters and the sandbox

Adapters run as separate programs. Four checks stand between an adapter and your server. None of them is enough on its own.

  1. 01

    Hash check

    An archive is imported only if its SHA-256 matches the one you give, or the one in a signed index. The program’s hash is recorded, and an adapter whose executable has changed is not started.

  2. 02

    Consent

    Enabling an adapter shows what it asks for, and asks. Nothing runs until you approve. An update that asks for more needs a new approval.

  3. 03

    A grant

    What an adapter may ask the daemon to do is limited by the grant you accepted, enforced by the daemon through the same policy, audit log and rate limits as everyone else.

  4. 04

    Sandbox

    On Linux, an adapter is started under Landlock (files) and seccomp, limited to what its manifest says. Where the kernel cannot enforce something, the consent screen says so.

What the sandbox does

  • Limits which files an adapter can read and write (Landlock).
  • Limits which system calls it can make (seccomp).
  • Keeps a buggy adapter from wandering into the rest of the system.

What it doesn’t do

  • It does not fully contain a hostile adapter. Only install adapters you trust.
  • It is a Linux feature. macOS: works, without the OS sandbox
  • It can’t enforce which hosts an adapter connects to. The manifest names them, and the consent screen says “Not enforceable per host”.
  • It can’t take back permissions you approved on the consent screen.
06

Reporting a problem

If you find a security issue in OxidePM or an adapter, please report it privately. Don’t open a public issue.
